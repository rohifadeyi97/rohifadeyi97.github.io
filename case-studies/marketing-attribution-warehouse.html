Case study / Python · SQL · Power BI

Marketing Attribution Warehouse

A synthetic, portfolio-safe recreation of a production marketing attribution system — connecting email and web engagement to revenue outcomes through a 32-table warehouse and a confidence-ranked matching model.

View live dashboard ↗ ← Back to all projects

01

Overview

Marketing and revenue systems don't share a key by default.

Email platforms, web analytics, and CRM systems each track engagement in their own way, with no shared identifier connecting a campaign click to an actual registration or order. This project builds that connection: a warehouse that ingests Constant Contact, GA4, Salesforce, and WooCommerce data, matches engagement to CRM contacts, and traces the chain through to registrations, material orders, and revenue.

This is the public version of a system originally built against a real production database for a workforce training and certification organization. The schema and matching logic are reproduced exactly; every row of data here is synthetically generated.

02

Approach

Confidence-ranked matching, not a single hard join.

Each engagement gets matched to a CRM contact through a ranked hierarchy — exact email match first, falling back to company-domain match when no exact match exists. Every match carries its confidence level and match type through to the report, so the dashboard shows not just attributed revenue but how certain that attribution actually is.

The warehouse itself is 32 tables across five source systems, built by a single Python loader that creates the schema, loads the data, and populates the attribution fact table Power BI reads from — one entry point, no manual SQL steps for a new environment to stand up.

04

What I'd do differently

The first version of the public loader approximated the production schema instead of matching it exactly — Power BI's compatibility failures made it clear that "similar" isn't sufficient when a report file has hard-coded expectations about table and column structure. A later pass also over-scrubbed some attribution fields during sanitization and broke the report's revenue visuals, which reinforced a rule I now apply earlier: separate presentation fields, which are safe to genericize, from model-critical fields, which have to be preserved exactly.
