I built a shared data and automation system that maintains branded playlists and powers a monthly Vinyl Club workflow. It handles the repetitive work around discovery, data cleanup, qualification, playlist updates, publishing, and tracking so the human role can stay focused on taste and final decisions.

01

Overview

The goal was to stop rebuilding the same music operation every month.

The project began with nine playlists across two brands. Keeping them fresh meant constantly finding new candidates, checking whether they fit, cleaning up provider metadata, managing duplicates, updating memberships, and remembering manual changes.

I turned those tasks into a reusable system. Later, I extended the same data layer to support Vinyl Club, where one album can lead to a researched shortlist, a human selection, a generated playlist, cross-platform publishing, and a content brief for the month.

What changed

Before Repeated research, manual updates, scattered provider data
↓
After One shared data layer with scheduled automation and human approval where it matters

02

Process

I connected data collection, decision rules, automation, and publishing into one workflow.

01 / Collect

Build a reusable catalog

Music data comes from multiple sources, then gets normalized into persistent artist, track, album, identity, and provenance records.

02 / Decide

Turn editorial rules into logic

Different playlists use different criteria. The system also tracks history, manual removals, confidence, duplicates, and provider availability.

03 / Automate

Handle recurring maintenance

Scheduled jobs discover candidates, refresh eligible playlists, sync updates, reconcile manual edits, and report quality without starting from scratch each time.

04 / Extend

Use the same system for Vinyl Club

The monthly workflow reuses the catalog and research layer for album recommendations, playlist generation, approval, Spotify and Apple publishing, and content support.

03

Engineering decisions

I redesigned the system when API limits started shaping the product.

An early version relied too heavily on Spotify for discovery. That created a slow and fragile process because of quotas, timeouts, and repeated lookups.

I moved broad discovery to a mix of Apple, editorial seeds, Last.fm, stored observations, and local MusicBrainz data. Spotify became a more focused verification source. I also cached resolved identities and preserved source history so the system could reuse work instead of paying for the same lookup again.

Architecture change

Provider-heavy Too many live lookups and too much dependence on one API
↓
Local-first and multi-source Reuse stored data, query providers when new evidence is actually needed

05

Takeaway

The project became more useful when I stopped thinking of it as playlist code.

The bigger lesson was about systems design. The real opportunity was not to automate taste. It was to automate the work around taste: collecting evidence, cleaning data, applying repeatable rules, tracking history, handling provider differences, and moving approved decisions into production.

That same pattern applies well outside music. Any recurring workflow that mixes research, business rules, human judgment, and execution can benefit from the same approach.

Tools: Python, SQL, REST APIs, webhooks, SQLite, MusicBrainz, Apple Music, Spotify, GitHub Actions, scheduled ETL, and persistent workflow state.
