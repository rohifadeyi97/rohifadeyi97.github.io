I built an interconnected music operations system that started as an autonomous playlist-maintenance engine and evolved into the data and automation backbone for a monthly Vinyl Club editorial workflow. The same infrastructure now handles discovery, identity resolution, qualification, playlist generation, manual overrides, cross-platform publishing, history, and content-ready output.

01

Business problem

What looked like playlist curation was really a recurring operations problem.

The original requirement was to keep nine branded playlists current across two music properties without manually rebuilding each one every cycle. That meant repeatedly discovering candidates, checking whether tracks actually fit, resolving inconsistent provider metadata, avoiding duplicates, applying different playlist rules, rotating membership, publishing updates, and remembering which human edits should persist.

Once that infrastructure existed, a second workflow became possible: use the same catalog, evidence, and provider logic to support a monthly Vinyl Club editorial process. Instead of creating another standalone tool, I extended the existing system so one data layer could support both always-on playlist maintenance and a higher-touch monthly recommendation and publishing workflow.

Without the system
  • Research candidates repeatedly
  • Resolve tracks across providers by hand
  • Remember playlist-specific rules
  • Refresh multiple playlists manually
  • Rebuild monthly editorial playlists from scratch
  • Track edits and publishing state manually
  • Create content context separately after publishing
→
With the system
  • Discovery becomes reusable data
  • Identity resolution is cached and normalized
  • Rules are encoded once
  • Recurring playlist refreshes are scheduled
  • Vinyl Club starts from the same evidence layer
  • Manual choices become durable workflow state
  • Publishing creates a content-ready monthly packet

02

System architecture

I treated music curation like a data product: collect once, normalize once, reuse everywhere.

01 / Ingest

Collect from multiple sources

Apple charts, editorial seed graphs, Last.fm, ListenBrainz, provider observations, and existing curated playlists expand the candidate universe without depending on a single API.

02 / Normalize

Create durable identities

Artists, tracks, albums, release metadata, provider IDs, source keys, ISRCs, and provenance are reconciled into persistent catalog records rather than re-resolved every time.

03 / Decide

Turn editorial rules into data logic

Theme scores, release age, source corroboration, recurrence, manual suppression, artist diversity, confidence, and playlist-specific policies determine what can qualify.

04 / Operate

Use the same state for multiple workflows

Scheduled playlist refreshes and the Vinyl Club email workflow both read from the same persistent history, provider mappings, evidence, and catalog infrastructure.

03

Workflow A / Autonomous playlists

The first layer removed the recurring maintenance burden from nine playlists.

01 / Discovery

Scheduled candidate generation

New music enters through Apple charts, seed relationships, Last.fm, and other observations instead of requiring repeated manual research for every list.

02 / Qualification

Different playlists use different rules

Throwbacks requires tracks to be at least ten years old; Anthems emphasizes recognition; Vibe, Party Starters, After Dark, Motivation, Meditation, Healing, and Focus use their own thematic evidence.

03 / Refresh

Membership rotates on schedule

Refresh jobs enforce artist diversity, quality floors, recurrence history, and different operating cadences rather than relying on someone to remember when each playlist needs attention.

04 / Reconciliation

Human edits survive automation

Manual additions and removals are observed and stored as events, so a scheduled refresh does not blindly undo an editorial correction.

Workflow B / Vinyl Club

The second layer turned that same infrastructure into a monthly editorial production workflow.

01 / START

Resolve the anchor An album or playlist link becomes the canonical starting point for the month.

02 / RESEARCH

Build a defensible shortlist Local reference data and bounded provider discovery find records connected through credits, context, and listening evidence.

03 / PICK

Keep the editorial decision human The editor chooses the two additional records instead of letting the scoring system silently make the final taste decision.

04 / DRAFT

Generate the monthly playlist Representative tracks from the three records are expanded with discovery-first tracks while deduplication and diversity rules protect quality.

05 / READY

Publish and package The approved state publishes across Spotify and Apple Music and generates a deterministic content packet for the month.

05

Data manipulation

The hard part was making inconsistent provider data usable as one decision layer.

Each source answers a different question. A chart can indicate current demand. A seed relationship can indicate editorial adjacency. Last.fm and ListenBrainz contribute behavioral or similarity context. Spotify and Apple provide availability and provider-native identity. MusicBrainz provides canonical releases, recordings, works, credits, and relationship structure.

I separated raw observations from normalized catalog entities, provenance, scores, recommendation evidence, manual events, and playlist state. That lets the system combine evidence without pretending every signal means the same thing, reuse previous identity work, audit where a candidate came from, and apply different logic depending on the workflow.

Shared transformation layer

Raw observations Charts · seed graphs · artist/title strings · provider IDs · audience signals · credits
↓
Normalized music intelligence Canonical identities · ISRCs · provenance · cached resolutions · relationships · history
↓
Workflow-specific decisions Autonomous refresh eligibility OR Vinyl Club bridge, sonic-fit, draft, and publishing logic

06

Engineering judgment

Provider limitations became architecture decisions instead of recurring operational failures.

An early version leaned too heavily on artist-by-artist Spotify discovery. It was straightforward, but repeated timeouts, quotas, and development-mode restrictions made it a poor backbone for unattended automation. Rather than keep increasing retries, I redesigned discovery around Apple, seed graphs, Last.fm, persisted catalog observations, and local MusicBrainz data.

Spotify became a bounded verification and playability source instead of the system's universal discovery engine. Apple publishing was made conservative as well: confident matches publish, unavailable tracks are skipped and reported, and uncertain substitutions are rejected. These choices made the workflow more reliable because provider uncertainty is treated as data, not hidden behind retries.

Provider-heavy Repeated live discovery and identity work
→
Local-first + cached Persisted catalog and MusicBrainz reference data do the reusable work
→
Bounded provider calls External APIs are used where they add new evidence or confirm playability

07

Recommendation design

For Vinyl Club, the system needed to understand the difference between “connected” and “sounds similar.”

01 / Bridge strength

Why does the record belong?

Credits, collaborators, works, and other verified relationships establish a defensible editorial connection. A style tag alone cannot qualify an album.

02 / Listening fit

Does the playlist still make sense?

Sonic and listening evidence leads expansion selection. Producer or songwriter relationships can support a track, but cannot fill the playlist by themselves.

03 / Discovery

Popularity should not choose the month

Recognition is not a positive ranking signal for Vinyl Club expansion. More obvious tracks receive a mild penalty so discovery can do useful work.

04 / Diversity

One collaborator cannot dominate

Relationship discovery and portfolio ranking spread attention across credited people, artists, and albums so one prolific producer or writer does not monopolize the output.

Business value

The time saving is structural: one reusable system replaced several recurring workflows.

01 / Reusable research

Discovery becomes an asset

Candidate observations, identities, relationships, and prior resolutions are stored and reused instead of being researched from zero for every playlist or month.

02 / Lower maintenance

Rules replace memory

Refresh cadence, theme requirements, recurrence controls, duplicate handling, and provider constraints are encoded in the system rather than carried as recurring manual checklist work.

03 / Lower API dependence

Cache first, query when valuable

Local reference databases and persistent provider observations reduce unnecessary calls and make the operation less fragile when an external provider is slow, unavailable, or quota-limited.

04 / More output per decision

One editorial choice feeds multiple channels

A monthly Vinyl Club decision does not stop at a playlist: the same frozen evidence feeds publication, reporting, and reusable editorial content.

11

What I learned

The project became more valuable when I stopped treating automation as a script and started treating it as an operating system.

The first useful insight was that “automate the playlist” was too narrow. A dependable system also needed source strategy, persistent state, provider fallbacks, quality controls, manual override handling, scheduling, provenance, and failure modes that stop safely.

The second was that the same infrastructure could support a different business workflow without being rebuilt. The autonomous playlists and Vinyl Club now share a common data foundation but use it differently: one optimizes recurring maintenance, while the other supports a deliberate monthly editorial decision. That is the part of the project I would reuse elsewhere — build the evidence layer once, then let multiple operational workflows consume it.

About time saved: I did not run a formal before/after time study, so I do not claim a fabricated number of hours. The measurable operational change is that discovery, normalization, qualification, refresh scheduling, synchronization, history, reconciliation, monthly research, playlist generation, publishing, and content preparation are now handled by reusable system components rather than recreated manually each cycle.
